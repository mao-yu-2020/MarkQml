# RenderMark Shared Library Design

**Date:** 2026-06-01  
**Status:** Approved  
**Scope:** Convert `RenderMark` from a static library to a shared (dynamic) library with proper cross-platform export/import macros and updated CMake package config for external QML consumers.

---

## 1. Background

`RenderMark` is currently built as a **static library** (`qt_add_library(RenderMark STATIC)`). The QML module is consumed via a static plugin that requires external projects to compile a `rendermark_plugin_import.cpp` file containing `Q_IMPORT_PLUGIN(RenderMarkPlugin)`.

The goal is to convert `RenderMark` into a **shared library** so that:
- C++ symbols are exported/imported correctly on Windows (`__declspec(dllexport/dllimport)`).
- On Linux/macOS, symbol visibility is controlled via `-fvisibility=hidden` + `__attribute__((visibility("default")))`.
- The QML module is loaded dynamically at runtime by the QML engine, eliminating the need for `Q_IMPORT_PLUGIN`.
- External projects can consume `RenderMark` via `find_package(RenderMark)` + `target_link_libraries(... RenderMark::RenderMark)` + setting a QML import path.

---

## 2. Architecture

### 2.1 Library Type

```cmake
qt_add_library(RenderMark SHARED)
```

When `qt_add_qml_module` is attached to a **SHARED** library, Qt 6 automatically generates a **dynamic QML plugin** (`RenderMarkplugin.dll`/`.so`/`.dylib`) instead of a static plugin. The QML engine loads this plugin automatically when an external project executes `import RenderMark` at runtime.

### 2.2 Export Macros

Use CMake's built-in `generate_export_header()` to produce `rendermark_export.h` at build time. The macro pattern is:

- **Building `RenderMark`**: `RENDERMARK_BUILD_SHARED_LIB` is defined → symbols are **exported**.
- **Consuming `RenderMark`**: no build macro defined → symbols are **imported** (default for external users).

Platforms:
- **Windows**: `__declspec(dllexport)` / `__declspec(dllimport)`
- **Linux/macOS**: `__attribute__((visibility("default")))`

All public C++ classes (`Mark`, `MarkNode`, `MarkTree`) receive `RENDERMARK_EXPORT` on their declarations.

### 2.3 Target Visibility & Include Directories

```cmake
target_include_directories(RenderMark
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}>
        $<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}>
        $<INSTALL_INTERFACE:include/RenderMark>
)
```

The build-directory include is required so that `rendermark_export.h` (generated inside the build tree) is found during compilation.

## 3. File Modifications

### 3.1 New File

- `rendermark_export.h` — auto-generated by `generate_export_header(RenderMark)` at build time.

### 3.2 Modified Files

| File | Change Summary |
|------|----------------|
| `RenderMark/CMakeLists.txt` | `STATIC` → `SHARED`; add `generate_export_header()`; update `target_include_directories`; split plugin install to QML path; remove static-plugin import file generation |
| `RenderMark/Mark.h` | Include `rendermark_export.h`; add `RENDERMARK_EXPORT` to class declaration |
| `RenderMark/MarkNode.h` | Same as above |
| `RenderMark/MarkTree.h` | Same as above |
| `RenderMark/cmake/RenderMarkConfig.cmake.in` | `STATIC IMPORTED` → `SHARED IMPORTED` for both `RenderMark` and `RenderMarkplugin`; add `IMPORTED_IMPLIB` for Windows; remove `rendermark_plugin_import.cpp` logic |
| `CMakeLists.txt` (root) | No structural changes required; `appMarkQml` continues to link `RenderMark` |

## 4. Installation Layout

```
<prefix>/
├── bin/
│   ├── RenderMark.dll                 (Windows only)
│   ├── cmark-gfm.dll                  (Windows, bundled)
│   └── cmark-gfm-extensions.dll       (Windows, bundled)
├── lib/
│   ├── RenderMark.lib                 (Windows import library)
│   ├── libRenderMark.so / .dylib      (Linux / macOS)
│   ├── cmark-gfm.lib                  (Windows, bundled)
│   ├── cmark-gfm-extensions.lib       (Windows, bundled)
│   └── qml/
│       └── RenderMark/
│           ├── qmldir
│           ├── RenderMark.qmltypes
│           └── RenderMarkplugin.dll / .so / .dylib
├── include/
│   └── RenderMark/
│       ├── Mark.h
│       ├── MarkNode.h
│       ├── MarkTree.h
│       └── rendermark_export.h
└── lib/cmake/RenderMark/
    ├── RenderMarkConfig.cmake
    └── RenderMarkConfigVersion.cmake
```

**Key point:** `RenderMarkplugin` is installed into `lib/qml/RenderMark/` so the QML engine can discover it alongside `qmldir`. The main `RenderMark` shared library remains in `lib/` (or `bin/` on Windows).

## 5. External Consumer Usage

After `cmake --install`:

```cmake
find_package(RenderMark REQUIRED)

target_link_libraries(MyApp PRIVATE RenderMark::RenderMark)

# In C++ main.cpp
engine.addImportPath(RenderMark_QML_IMPORT_PATH);
```

```qml
// In MyApp.qml
import RenderMark

Mark { id: parser }
```

No `Q_IMPORT_PLUGIN`, no `rendermark_plugin_import.cpp`, and no manual `.qml` file copying is required.

---

## 6. Cross-Platform Notes

| Platform | Shared Library | QML Plugin | Notes |
|----------|---------------|------------|-------|
| Windows | `RenderMark.dll` + `RenderMark.lib` (implib) | `RenderMarkplugin.dll` | `IMPORTED_IMPLIB` must be set in `RenderMarkConfig.cmake.in` |
| Linux | `libRenderMark.so` | `libRenderMarkplugin.so` | Standard `.so` linkage; `LD_LIBRARY_PATH` or `rpath` needed at runtime |
| macOS | `libRenderMark.dylib` | `libRenderMarkplugin.dylib` | Standard dylib linkage; `@rpath` or `DYLD_LIBRARY_PATH` needed |
| Android | `libRenderMark.so` | `libRenderMarkplugin.so` | cmark-gfm is statically linked on Android; no extra DLL deployment |

---

## 7. Out of Scope

- Changing cmark-gfm from dynamic to static on Windows (it is already dynamic via vcpkg).
- Modifying QML style/theme logic (unrelated).
- Adding `BUILD_SHARED_LIBS` toggle to support both static and dynamic in one build tree (explicitly decided as "shared only").

---

## 8. Verification Steps

1. `cmake --build` succeeds (7/7 targets).
2. `cmake --install` produces the layout described in Section 4.
3. A fresh external CMake project can `find_package(RenderMark)` and link successfully.
4. The external project's QML can `import RenderMark` and instantiate `Mark`, `MarkTree`, `MarkNode`.
5. On Windows, `dumpbin /exports RenderMark.dll` shows exported `Mark`, `MarkNode`, `MarkTree` symbols.
